Your organization has 50,000 activity records and growing. You open the dashboard and wait 8 seconds for it to load. Your sustainability team is frustrated. Your auditors are asking why the reports take so long to generate.

This is a scale problem, not a design problem.

Most carbon accounting platforms query raw emissions data at dashboard time. They calculate totals on every page load. With 50k records, every query touches thousands of rows. With 500k records, pages become unusable.

CarbonSite takes a different approach: pre-compute aggregations and keep them up to date.

## The Naive Approach (and Why It Fails)

Query all activity records, group by facility/category/period, sum emissions, return results.

```sql
SELECT 
  facility_id, 
  category_id, 
  SUM(co2e_kg) as total_emissions
FROM activity_records
WHERE organization_id = ? AND reporting_period_id = ?
GROUP BY facility_id, category_id
```

With 50k records: ~100ms query time. Acceptable.
With 100k records: ~200-300ms query time. Noticeable but okay.
With 500k records: ~1-2 second query time. Bad.
With 1M+ records: ~5+ second query time. Unusable.

The problem scales linearly. Every row added makes queries slower.

## CarbonSite's Approach: Materialized Aggregations

Instead of computing aggregations at query time, CarbonSite maintains pre-computed summary tables called DashboardAggregate:

```sql
CREATE TABLE dashboard_aggregate (
  organization_id UUID,
  reporting_period_id UUID,
  facility_id UUID,
  category_id UUID,
  scope1_co2e_kg DECIMAL,
  scope2_co2e_kg DECIMAL,
  scope3_co2e_kg DECIMAL,
  total_co2e_kg DECIMAL,
  last_updated TIMESTAMP,
  record_count INTEGER
);

CREATE INDEX ON dashboard_aggregate 
  (organization_id, reporting_period_id, facility_id);
```

When you load a dashboard for a reporting period, you query this pre-computed table:

```sql
SELECT * FROM dashboard_aggregate
WHERE organization_id = ? AND reporting_period_id = ?
```

Result: <1ms query, regardless of how many individual records exist.

## Incremental Updates

The trick is keeping DashboardAggregate current as data changes.

Instead of rebuilding the entire summary table every time a calculation runs (expensive), CarbonSite uses incremental updates:

1. **Calculation runs** — produces 5,000 new emissions calculations for a facility
2. **Batch insert** — inserts new calculations into activity_records
3. **Aggregate update** — updates the single DashboardAggregate row for that facility:
   ```sql
   UPDATE dashboard_aggregate
   SET total_co2e_kg = total_co2e_kg + (new calculations sum),
       record_count = record_count + 5000,
       last_updated = NOW()
   WHERE organization_id = ? AND facility_id = ? AND reporting_period_id = ?
   ```
4. **Result** — dashboard updates instantly, takes milliseconds

CarbonSite maintains multiple materialized views depending on query patterns:

**By Facility:**

- Peer comparison

**By Category:**
- Top emission sources
- Changes month-to-month

**By Facility + Category:**
- Drill-down view

Each view is updated incrementally when calculations change. Queries against these views are blazingly fast.

## Storage Trade-Off

Pre-computing aggregations uses extra storage: one row per (org, period, facility, category) combination.

For a typical organization:
- 100 facilities × 20 categories × 12 periods = 24,000 summary rows
- Each row: ~150 bytes
- Total: ~3.6 MB

This is negligible storage cost for massive speed gains.

## When Aggregates Rebuild

Occasionally you need to rebuild aggregates from scratch:

- Methodology changes (DEFRA factors updated)
- Calculation engine bug fixed
- Data correction applied retroactively
- Audit request requires re-verification

CarbonSite rebuilds aggregates by:

1. Identify affected calculations (all for the period)
2. Recalculate from source data (happens in background)
3. Update DashboardAggregate rows incrementally
4. Freeze new snapshot

Users continue working on old dashboard while rebuild happens in background.
