# Dashboard, charts, saved views and forms

Moved word for word out of CLAUDE.md so it is read only when working in this area (``app/(app)/orgs/[orgId]/dashboard`, `lib/dashboard/`, `lib/saved-views/`, `lib/map/`, `components/forms/``). CLAUDE.md keeps the rules that apply everywhere and an index of these files.

**Dashboard slices** (`DashboardSlice`, `lib/calculation/dashboard-slices.ts`, `snapshot-slices.ts`, migration `20260930000063`): the base-grain table behind the portal's supplier, site, contract and month filters (design: `docs/PORTAL_EXPERIENCE_DESIGN.md`). `DashboardAggregate` pre-writes each rollup, so adding dimensions there would multiply rows; a slice table holds exactly one row per distinct combination of scope, Scope 2 method, category, facility, site, contract, normalised supplier key (`supplierKey()`) and month, so any subset sums each calculation once. It is written in the same transaction as the aggregates (`rebuildDashboardAggregates()`; the Scope 2 row rule is shared through `reportingRows()`, so purchased heat sits under both methods when the run has market-based electricity and readers pin the method with `PRIMARY_SCOPE2_METHOD`), copied onto each published snapshot by `copyLiveSlicesToSnapshot()` in both snapshot routes, and cleared by the platform org reset. facility, site and contract ids are plain columns (a snapshot survives a later site or contract deletion). **The dashboard reads it** for its supplier, month range and scope filters (`lib/dashboard/slice-filter.ts`, `components/dashboard/dashboard-filter-bar.tsx`, URL keys `supplier`, `from`, `to` as `YYYY-MM`, `scope`; saved as views like the other dashboard filters): `parseSliceFilter()` drops malformed values, `sliceWhere()` is always inside the organisation and period, live slices only, `PRIMARY_SCOPE2_METHOD`, under any entity/country/contract facility scope; the supplier text is normalised by `supplierKey()` and matched as a fragment. With one set, the headline, scope split, top categories and facility breakdown come from slices (`loadSliceView()`, same shape as the aggregate reads); the period trend and the year-on-year comparison follow the same filters too (`loadSliceTrend()`, `loadSliceScopes()`: the same slices across every period, so the change shown is like for like), while the energy, transport, water and industry panels and the snapshot banner stay organisation-wide and the bar says so, and a record with no date drops out once a month is set. Checked in a browser on a scratch tenant: totals match the aggregates (73.07 t unfiltered, 21.24 t Scope 2, 35.99 t for one supplier). **Project** (`projectId`) resolves to the project's sites inside the organisation (`resolveSliceRefs()`; another organisation's project has no sites here and matches nothing) and filters slices by `siteId`. When that filter empties the scope panel but the period has live rollups, the panel says the period has figures and none reach the project, with no fix link, because the cause is records with no site. The web record form (Project site field), the import commit (site picker beside Commit), add-from-bill, the Zapier record action, supplier request convert and supplier report accept set `siteId` (optional body field on the API ones), and every route checks it with `orgRefsError()`; commuting imports and field-submission approval already set it, while records derived from a `WasteRecord` stay unassigned because that table has no site; records written before that stay unassigned, since `Site` has no facility link to infer one from. "No calculation run" appears only when the period has no live rollups (`lib/dashboard/empty-state.ts`). **Site** (`siteId`, set by a hero pin or list row for a project site) filters slices to that one `Site`, inside the organisation and inside a chosen project's sites, never beyond them (`sliceWhere()`); an office or depot pin still sets `facilityId`; the id is a plain id and a saved view checks it with `orgRefsError()`. **Social value** (`sv=1`) is a record-set filter: only contracts with a commitment that is not cancelled (`SvCommitment`), and the bar shows those commitments' count and GBP-committed value beside the emissions, never added to them (`socialValueBeside()`; other currencies are counted, not summed). Both are saved as views, ids checked with `orgRefsError()` (`projectId`); tenancy: `tests/security/dashboard-slice-filters-tenancy.test.ts`. **Flagship charts** (`components/charts/kit/`, `lib/charts/`; visx scales and d3-shape/d3-sankey, no Recharts): `ChartFrame` gives every chart a Chart / Table switch with the same numbers; `SankeyChart` (scope to category to site, small categories and sites folded into Other nodes so nothing is dropped; reads the same slices as the filters and reconciles with the aggregate scope rollups, `lib/charts/__tests__/flows-reconciliation.test.ts`), `WaterfallChart` (previous total, biggest category movers, other, current total from live `DashboardAggregate` category rows of the two latest periods; hidden under any filter) and `PathwayChartKit` (the transition plan page: benchmark dashed, target, planned step line, actual dots; arrow keys move between years with a live-region read-out). Series use the validated scope palette plus slate, direction and series are also carried by dashes, dots, arrows and signs. Charts have focusable marks with labels. d3-sankey licence is in `docs/THIRD_PARTY_SOURCES.md`. Recharts remains on other pages until migrated. **Customisable dashboard** (phase 3 of the portal design; `lib/dashboard/widgets.ts`, `layout-store.ts`, `components/dashboard/dashboard-grid.tsx`, `DashboardLayout`, migration `20261004000065`, `/api/orgs/{orgId}/dashboard-layout`): the dashboard's blocks are 16 widgets (a registry: id, title, default width, optional roles) built on the server under the viewer's role and laid out by `DashboardGrid` (dnd-kit; the Move button picks a widget up and the arrow keys move it, plus buttons for half/full width, Hide and an Add widget list, so every edit has a keyboard path). A layout is only ids, order, widths and hidden ids, never data. Resolution: the person's layout, else the organisation's default (`userKey` "org", set by admins only, audit `dashboard_layout.org_default_changed`), else the master preset (`presetLayout()`, the same for every role: the analytical panels first, see line 32). A widget added to the product later is placed last and shown; a role that may not have a widget (Run a calculation) never gets it laid out or rendered; an invalid stored layout is ignored. "Reset my layout" deletes the personal row. **Forms** (`components/forms/form-kit.tsx`): one layout language for portal forms. `FormSection` (heading plus a one-line purpose, a four-column grid that is one column on a phone), `FormField` (label above, hint or error below, `optional` only where most fields are required, `span` 1 to 4), `FormDisclosure` (native details for rarely used fields), `FormError` and `FormActions` (one bar, primary last, destructive apart on the left). New forms use it; do not write another local `Field`. Container-query grid: `FormSection` takes `cols` (2, 3 or 4) and columns follow the width of the container (`@md`, `@xl`), so one form reads the same on a page, in a panel and in a dialog; `span` 4 is a full row. `fieldClass` is the border, radius and focus ring for native inputs, selects and textareas beside the shadcn `Input`; `components/structured-forms/ms-fields.tsx` (`inputCls`, `labelCls`, `FieldRow`) uses it too. `FormField` takes `aside` for a small link on the label row. **"Optional" is shown only where the form said so or used the star convention** (an unmarked field is required): do not add `optional` on a guess. Migrated: facilities (`settings/operations/facilities-panel.tsx`, one form for add and edit), record entry, report request and bid pack, organisation profile, periods, business units, imports, embodied carbon, targets and initiatives, SBTi, waste, water, offsets, social value (log, target, obligations, supplier, activities, commitments), contracts, projects, sites, subcontractors, PAS 2080, PPN 026, plant, case studies, branding, tenders watch, webhooks, management systems (adoption, requirement, register form) and the editors that already had step sections (incident, permit, assurance, biodiversity). Left as they were on purpose: sign-in, sign-up and reset pages, payment, the marketing contact form, saved-views menu, page filter bars and the checkbox-only data retention form. Tooling for further migrations is not in the repo: convert a label-and-control pair to `FormField`, group fields into titled `FormSection`s, end with `FormError` and `FormActions`. **Address search** fills the street line only in its box and sets country, region and postcode on pick; with no country chosen the organisation's home country is passed to Geoapify as a bias (`bias=countrycode:`), so a UK site is not offered US streets first. A 503 from the route carries `details.reason` (`no_key`, `unreachable`, `status_<code>`) and the picker shows it.

**Saved views** (`SavedView`, `lib/saved-views/`, `app/api/orgs/{orgId}/saved-views`, migration `20260930000064`): a named set of filters for one portal page, private to its owner or shared with the organisation. It stores the request, never results, so opening a view reads current data under the viewer's own role. `SURFACES` (`lib/saved-views/index.ts`) lists each page and the filter keys it reads from its URL (`dashboard`: facilityId, contractId, entityId, country, supplier, from, to, scope); a page joins by adding itself there. `checkFilters()` refuses any other key (country must be an ISO-2 code), and ids are checked against the organisation with `orgRefsError()` on create and on every filter change (`entityId` as `legalEntityId`). Who may do what: viewers of the inventory plus contract and project managers keep personal views (`viewRoles()`, 50 per person per page, unique name per person and page); only editors and admins share (`mayShare()`); the owner changes or deletes their own, and an admin may also change or delete a shared one, never someone's private one (`mayChangeView()`); a view is looked up inside the organisation and only among the caller's own or shared ones. Creating, changing or deleting a shared view is audit-logged (`saved_view.*`); personal churn is not. `GET` returns `href` for each view, built by `viewHref()`. Tests: `lib/saved-views/__tests__`, `tests/security/saved-views-tenancy.test.ts`. **The dashboard shows a "Views" menu** (`components/saved-views/saved-views-menu.tsx`, above the entity and country filters, only for `viewRoles()`): my views and shared ones (with the sharer's name), open a view (a plain link to the page with its filters, so the URL is the state), save the filters now set (the menu item is disabled with none set), share (editors and admins only; the control is hidden otherwise, the server decides) and delete (own views, and shared ones for admins; open and delete are sibling menu items so both are keyboard reachable). Tests: `components/saved-views/__tests__` (first component test in the repo, React Testing Library with `fireEvent`; Radix menus open from the keyboard in jsdom). **The records page filters through the URL** (`records/records-filters.tsx`, `records` in `SURFACES`): period, category, status, facility, contract, project site (`siteId`) and a supplier name fragment; native selects, the URL is the state (`router.replace`), the server page reads `searchParams` and the table refetches from its first page when the set changes, so a filtered list can be bookmarked, shared or saved from the same Views menu. `GET /api/orgs/{orgId}/activity-records` accepts `periodId`, `categoryId`, `reviewStatus` (enum, 422 otherwise), `facilityId`, `contractId`, `siteId` and `supplier` (case-insensitive contains, up to 64 characters); every filter narrows inside the organisation in the URL and none can widen it (`tests/security/activity-records-list-scope.test.ts`). Saved views on this page check the period, facility and contract ids against the organisation. **The suppliers page filters through the URL too** (`suppliers/page.tsx` is now a server page: it reads `searchParams`, offers the Views menu to `viewRoles()` and sends a signed-out visitor to sign in; `suppliers-filters.tsx` and `suppliers-table.tsx` are the client parts): name search (`q`), health band (`health`: healthy at 80 and above, at risk at 60, critical below; `healthOf()` in `lib/suppliers/filter.ts`, which the table's badge uses) and `trend`. The list API returns every supplier at once, so `filterSuppliers()` narrows it in the browser without a refetch. Fixed-list filters are validated by `ENUM_FILTERS` in `lib/saved-views` for every surface (review status, health, trend). **The submissions queue filters through the URL too** (`submissions/submissions-filters.tsx`, `lib/field-submissions/list-filters.ts`): the existing status tabs plus document type, period, facility and contract, all in the URL and saveable as views. `parseSubmissionFilters()` keeps only known keys with valid values (an old or malformed link still opens the page, unknown values are dropped, not refused) and `submissionWhere()` builds the where, always inside the organisation; the tab counts count each status under the other filters (`submissionWhere(..., false)`), the SLA banner stays organisation-wide. The tabs' links keep the other filters. The table's own cursor paging is dormant (the page loads `limit` rows and "Show more" reloads), so filters apply on the server only. **The calculations page filters through the URL too** (`calculations/calculations-filters.tsx`, `lib/calculation/run-list-filters.ts`): status, period and factor library (every library, so old runs can be found), saved as views like the other pages. `parseRunFilters()` drops unknown or malformed values instead of refusing, `runWhere()` always scopes to the organisation; the runs list still shows the newest 50 matching runs and the summary pills describe that list. A filter that matches nothing says so, rather than showing the first-run empty state. `ENUM_FILTERS` in `lib/saved-views` is now per page, because `status` means a submission status on one page and a run status on another. That completes the first four pages (dashboard, records, suppliers, submissions, calculations); any other page joins by adding itself to `SURFACES` and moving its filters into the URL.

**Arabic** (`i18n/request.ts`, `messages/{en,ar}.json`, `lib/i18n/ui-locale.ts`): the app's own screens are English. Strings are served by `next-intl` in its no-routing mode: the language is the `ui_lang` cookie, there is no middleware and no URL change, and only layouts that render a `NextIntlClientProvider` read the cookie (today only `(auth)`), so the marketing pages stay static. Arabic is a **pilot on the sign-in screen only**, behind `NEXT_PUBLIC_ENABLE_ARABIC_UI=true`, with a language switch (`components/i18n/ui-locale.tsx`) and `dir`/`lang` set on the sign-in panel. A missing translation falls back to English key by key (`mergeMessages()`); a test keeps the Arabic keys in step with the English. Its wording has not had a native review. To translate a screen: add its strings to both JSON files, call `useTranslations("<namespace>")`, and wrap its layout in `NextIntlClientProvider`. **Report PDFs have no Arabic support**: an embedded-font attempt was removed on the owner's instruction, so Arabic text in a report depends on the server's fonts and will print as empty boxes on Vercel. Not done: translating the rest of the app, an RTL layout audit (logical CSS properties), Arabic report text. Free monitoring and log drain steps: `docs/OPERATIONS_MONITORING.md`.

The dark stylesheet (`app/dark-theme.generated.css`, imported by `app/globals.css`) has two parts. Tailwind palette variables are redefined with the shade swapped (50 and 950, 100 and 900, and so on), and white and black are inverted; surfaces map onto a near-white ladder so cards still sit above the page. Arbitrary hex classes (`text-[#111827]`, `bg-[#F8F9FA]`) are not variables, so the generator writes one rule per class the source uses, including hover, focus, group-hover, placeholder, divide and opacity suffixes. Regenerate after adding a hex class with `pnpm theme:build` (`scripts/build-dark-theme.ts`, `lib/theme/dark-css.ts`); `lib/theme/__tests__/dark-css.test.ts` fails while the committed file is stale and fails on any hex class with no dark rule. Tenant branding colours do not carry into dark mode, by design.

Limits: colours written inline in `style` attributes, SVG, chart and map fills (recharts, MapLibre) and class names built at run time are not covered by the generated rules; they keep their light value until they are moved onto a class the generator sees. `text-white` on a dark fill becomes dark under the inversion, so check primary buttons in dark mode after a change. Tests: `lib/theme/__tests__/preference.test.ts` (choice parsing, resolution, the init script against fake document and location), `app/api/me/theme/__tests__/route.test.ts`.
