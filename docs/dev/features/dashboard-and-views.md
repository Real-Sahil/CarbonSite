# Dashboard, charts, saved views and forms

Moved word for word out of CLAUDE.md so it is read only when working in this area (``app/(app)/orgs/[orgId]/dashboard`, `lib/dashboard/`, `lib/saved-views/`, `lib/map/`, `components/forms/``). CLAUDE.md keeps the rules that apply everywhere and an index of these files.

**Dashboard slices** (`DashboardSlice`, `lib/calculation/dashboard-slices.ts`, `snapshot-slices.ts`, migration `20260930000063`): the base-grain table behind the portal's supplier, site, contract and month filters (design: `docs/PORTAL_EXPERIENCE_DESIGN.md`). `DashboardAggregate` pre-writes each rollup, so adding dimensions there would multiply rows; a slice table holds exactly one row per distinct combination of scope, Scope 2 method, category, facility, site, contract, normalised supplier key (`supplierKey()`) and month, so any subset sums each calculation once. It is written in the same transaction as the aggregates (`rebuildDashboardAggregates()`; the Scope 2 row rule is shared through `reportingRows()`, so purchased heat sits under both methods when the run has market-based electricity and readers pin the method with `PRIMARY_SCOPE2_METHOD`), copied onto each published snapshot by `copyLiveSlicesToSnapshot()` in both snapshot routes, and cleared by the platform org reset. facility, site and contract ids are plain columns (a snapshot survives a later site or contract deletion). **The dashboard reads it** for its supplier, month range and scope filters (`lib/dashboard/slice-filter.ts`, `components/dashboard/dashboard-filter-bar.tsx`, URL keys `supplier`, `from`, `to` as `YYYY-MM`, `scope`; saved as views like the other dashboard filters): `parseSliceFilter()` drops malformed values, `sliceWhere()` is always inside the organisation and period, live slices only, `PRIMARY_SCOPE2_METHOD`, under any entity/country/contract facility scope; the supplier text is normalised by `supplierKey()` and matched as a fragment. With one set, the headline, scope split, top categories and facility breakdown come from slices (`loadSliceView()`, same shape as the aggregate reads); the period trend and the year-on-year comparison follow the same filters too (`loadSliceTrend()`, `loadSliceScopes()`: the same slices across every period, so the change shown is like for like), while the energy, transport, water and industry panels and the snapshot banner stay organisation-wide and the bar says so, and a record with no date drops out once a month is set. Checked in a browser on a scratch tenant: totals match the aggregates (73.07 t unfiltered, 21.24 t Scope 2, 35.99 t for one supplier). **Project** (`projectId`) resolves to the project's sites inside the organisation (`resolveSliceRefs()`; another organisation's project has no sites here and matches nothing) and filters slices by `siteId`. **Site** (`siteId`, set by a hero pin or list row for a project site) filters slices to that one `Site`, inside the organisation and inside a chosen project's sites, never beyond them (`sliceWhere()`); an office or depot pin still sets `facilityId`; the id is a plain id and a saved view checks it with `orgRefsError()`. **Social value** (`sv=1`) is a record-set filter: only contracts with a commitment that is not cancelled (`SvCommitment`), and the bar shows those commitments' count and GBP-committed value beside the emissions, never added to them (`socialValueBeside()`; other currencies are counted, not summed). Both are saved as views, ids checked with `orgRefsError()` (`projectId`); tenancy: `tests/security/dashboard-slice-filters-tenancy.test.ts`. **Flagship charts** (`components/charts/kit/`, `lib/charts/`; visx scales and d3-shape/d3-sankey, no Recharts): `ChartFrame` gives every chart a Chart / Table switch with the same numbers; `SankeyChart` (scope to category to site, small categories and sites folded into Other nodes so nothing is dropped; reads the same slices as the filters and reconciles with the aggregate scope rollups, `lib/charts/__tests__/flows-reconciliation.test.ts`), `WaterfallChart` (previous total, biggest category movers, other, current total from live `DashboardAggregate` category rows of the two latest periods; hidden under any filter) and `PathwayChartKit` (the transition plan page: benchmark dashed, target, planned step line, actual dots; arrow keys move between years with a live-region read-out). Series use the validated scope palette plus slate, direction and series are also carried by dashes, dots, arrows and signs. Charts have focusable marks with labels. d3-sankey licence is in `docs/THIRD_PARTY_SOURCES.md`. Recharts remains on other pages until migrated. **Customisable dashboard** (phase 3 of the portal design; `lib/dashboard/widgets.ts`, `layout-store.ts`, `components/dashboard/dashboard-grid.tsx`, `DashboardLayout`, migration `20261004000065`, `/api/orgs/{orgId}/dashboard-layout`): the dashboard's blocks are 16 widgets (a registry: id, title, default width, optional roles) built on the server under the viewer's role and laid out by `DashboardGrid` (dnd-kit; the Move button picks a widget up and the arrow keys move it, plus buttons for half/full width, Hide and an Add widget list, so every edit has a keyboard path). A layout is only ids, order, widths and hidden ids, never data. Resolution: the person's layout, else the organisation's default (`userKey` "org", set by admins only, audit `dashboard_layout.org_default_changed`), else the role's preset (`presetLayout()`: managers, admins and editors get everything in the long-standing order; sustainability directors, viewers, auditors and verifiers an executive short list; reviewers a review-centred one; the rest stay under Add widget). A widget added to the product later is placed last and shown; a role that may not have a widget (Run a calculation) never gets it laid out or rendered; an invalid stored layout is ignored. "Reset my layout" deletes the personal row. Tests: `lib/dashboard/__tests__/widgets.test.ts`, `components/dashboard/__tests__/dashboard-grid.test.tsx`, `tests/security/dashboard-layout-api.test.ts`. **Cross-filtering and drill-down** (phase 4): clicking (or Enter on) a flow diagram node sets `scope`, `categoryId` or `facilityId` in the URL (clicking again clears), a waterfall category bar sets `categoryId`; the headline, scopes, categories, facilities and flow all follow through the slice table, a chosen facility narrows inside any entity, country or contract scope and never beyond it, chips clear one filter each, and "Open the records behind this" links to the records page with the filters it supports (period, category, facility, contract, supplier); `lib/dashboard/__tests__/cross-filter.test.ts` holds that every panel's total is the same for the same filters. **Short menu** (`SIMPLE_MENU` in `components/org-sidebar.tsx`, localStorage `metricora:sidebar:all-pages`): the sidebar starts on seven job-named groups (Add data, To review, On site, Contracts and value, Reports, Plans and targets, Settings), always open, for every role except admin, sustainability director and auditor, who start on the full menu; "Show all pages" / "Show the short menu" at the foot switches and remembers per browser. Items are looked up by path in the full, role-filtered menu, so a role never sees a page it may not open; add a page to the short menu by adding its path to a group there. **Cards:** the getting-started checklist (`dashboard/onboarding-checklist.tsx`, progress ring, one "Next" button, step numbers), the task launcher (icon per destination) and register results (`waste/documents/register-result.tsx`, `RegisterResultCard`: status chip, facts list, plain note, licence line; tone is also in the icon and words) share one look: white rounded-2xl, slate border, soft shadow, orange accent, hover lift under `motion-reduce`. Use `RegisterResultCard` for any new public-register result. **Quick find understands sentences** (`paletteMatches()`): filler words are dropped, plurals folded and a few everyday words mapped (rubbish to waste, invoice to bill); every remaining word must match as before, and only for three or more meaningful words, when nothing holds them all, the pages holding at least half are offered, closest first. No model is involved; an AI "ask where to find it" box is not built. **Quick find** (`components/org/command-palette.tsx`, Ctrl or Cmd+K or the sidebar's ⌘K button): pages from `lib/nav/palette-items.ts` (a test checks each is a real page, and roles only see what the sidebar would offer) and saved views (fetched on open). **Record detail panel** (records page, "Details"): a side panel from the org-scoped record API with the latest calculation's figure, formula, factor library and warnings, and evidence. **Site map pins (fixed 9 October 2026):** the map used to read `Facility` only, and a facility had a position only when someone chose a suggested address, so most organisations saw a map with no pins and only a small note below it. It now shows two kinds of pin, offices and depots (`Facility`, own position, else placed from its postcode) and **project sites** (`Site`, placed from its UK postcode through postcodes.io; results kept per server instance in `lib/map/load.ts`), with project-site totals read from the snapshot's `DashboardSlice` rows by `siteId` (Scope 2 method pinned). Totals and shares are per kind, never added across kinds (an office and the site it serves count the same tonnes). A banner above the map says how many locations are placed and where to add the rest; clicking a pin (or its name in the table) selects it and opens a panel with figures and links (dashboard filtered to the facility or project, records for a facility). A project site's own position (`Site.latitude`/`longitude`, migration `20261010000091`, set by the address search on the New site form) wins over its postcode and works outside the UK; a site with neither, or a non-UK postcode and no search result, stays unplaced. **Site map and time scrubber** (phase 5; sidebar → Data → Site map, `/orgs/{orgId}/map`, `lib/map/`, `components/map/site-map.tsx`, `GET /api/orgs/{orgId}/map-data?snapshotId=`): sites sized by their emissions in one published snapshot (per-facility aggregates summed across scopes), a slider and Earlier/Later buttons across the organisation's published snapshots (fetched once each, a snapshot of another organisation is 404), and a table that always carries the same figures. Tiles load only when `NEXT_PUBLIC_MAP_STYLE_URL` is set (MapLibre 5; OpenFreeMap terms and privacy note in `docs/THIRD_PARTY_SOURCES.md`); without it a schematic plots the same positions and no request leaves the page; sites without a position are listed as not placed. Checked in a browser on a scratch tenant, including MapLibre rendering against a local blank style. Tests: `lib/map/__tests__`, `components/map/__tests__`, `tests/security/map-data-tenancy.test.ts`. **Assisted reporting** (phase 6; `lib/insights/`, `lib/reports/narrative-*.ts`, `ReportNarrative`, migration `20261004000066`): **Report summary** (Reports → "Write the summary page", `/orgs/{orgId}/reports/narrative`, `/api/orgs/{orgId}/report-narratives/{periodId}` GET for editors and reviewers, PUT and DELETE for editors, audit `report_narrative.saved|deleted`): the team writes the executive summary, key findings and recommendations of its inventory reports in a Tiptap editor limited to paragraphs and one bullet list (`narrative-text.ts` turns the document into the plain text a report prints, ignoring anything else). One row per organisation and period. When one exists the report worker uses it instead of calling a model (`loadTeamNarrative()`), and the page says who wrote it (`narrativeLabel()`: "Written by the reporting team", with "starting from an AI-assisted draft that the team reviewed and edited" when it began as one; generated wording is labelled AI-assisted in both the HTML and PDFKit layouts). With none saved and AI off, reports are exactly as before; `NO_NARRATIVE_TYPES` (`narrative-types.ts`) lists the layouts that never carry a summary, and a saved narrative's `updatedAt` joins the report's idempotency hash only when one exists, so an edited narrative never returns a stale PDF. **Draft with AI** (`POST .../report-narratives/{periodId}/draft`, editors, 10 a minute, 409 `AI_ASSIST_OFF`): the model sees only the period's figures (latest published snapshot's, else live; `loadPeriodFacts()`), the reply must follow the structure and every number in it must be one of the figures supplied (`ungroundedNumbers()`), otherwise 422 `DRAFT_REJECTED`; nothing is saved until a person saves. **Explain this change** (under the dashboard waterfall, `POST /api/orgs/{orgId}/insights/explain-change`, readers): the plain account of what moved is computed from the waterfall steps (`changeSummary()`, no model); with `ai: true` and AI assistance on, a model may add one paragraph, used only if grounded, labelled AI-assisted, and the route never calls a model when the organisation has not turned AI on. Tests: `lib/insights/__tests__`, `lib/reports/__tests__` (template labels, text conversion), `tests/security/report-narratives.test.ts`. The per-facility aggregate rows are written one per scope, so the facility breakdown sums them by facility (it used to list a facility once per scope). `dashboard-slices.test.ts` reconciles it with `groupDashboardAggregates()` through the real aggregate filters; a scratch Postgres run gave identical totals (141,686.583 kg) from slices and aggregates for the golden organisation. Social value is a different domain (`SvActivity`) and stays a record-set filter, never added to emissions.

**Forms** (`components/forms/form-kit.tsx`): one layout language for portal forms. `FormSection` (heading plus a one-line purpose, a four-column grid that is one column on a phone), `FormField` (label above, hint or error below, `optional` only where most fields are required, `span` 1 to 4), `FormDisclosure` (native details for rarely used fields), `FormError` and `FormActions` (one bar, primary last, destructive apart on the left). New forms use it; do not write another local `Field`. Container-query grid: `FormSection` takes `cols` (2, 3 or 4) and columns follow the width of the container (`@md`, `@xl`), so one form reads the same on a page, in a panel and in a dialog; `span` 4 is a full row. `fieldClass` is the border, radius and focus ring for native inputs, selects and textareas beside the shadcn `Input`; `components/structured-forms/ms-fields.tsx` (`inputCls`, `labelCls`, `FieldRow`) uses it too. `FormField` takes `aside` for a small link on the label row. **"Optional" is shown only where the form said so or used the star convention** (an unmarked field is required): do not add `optional` on a guess. Migrated: facilities (`settings/operations/facilities-panel.tsx`, one form for add and edit), record entry, report request and bid pack, organisation profile, periods, business units, imports, embodied carbon, targets and initiatives, SBTi, waste, water, offsets, social value (log, target, obligations, supplier, activities, commitments), contracts, projects, sites, subcontractors, PAS 2080, PPN 026, plant, case studies, branding, tenders watch, webhooks, management systems (adoption, requirement, register form) and the editors that already had step sections (incident, permit, assurance, biodiversity). Left as they were on purpose: sign-in, sign-up and reset pages, payment, the marketing contact form, saved-views menu, page filter bars and the checkbox-only data retention form. Tooling for further migrations is not in the repo: convert a label-and-control pair to `FormField`, group fields into titled `FormSection`s, end with `FormError` and `FormActions`. **Address search** fills the street line only in its box and sets country, region and postcode on pick; with no country chosen the organisation's home country is passed to Geoapify as a bias (`bias=countrycode:`), so a UK site is not offered US streets first. A 503 from the route carries `details.reason` (`no_key`, `unreachable`, `status_<code>`) and the picker shows it.

**Saved views** (`SavedView`, `lib/saved-views/`, `app/api/orgs/{orgId}/saved-views`, migration `20260930000064`): a named set of filters for one portal page, private to its owner or shared with the organisation. It stores the request, never results, so opening a view reads current data under the viewer's own role. `SURFACES` (`lib/saved-views/index.ts`) lists each page and the filter keys it reads from its URL (`dashboard`: facilityId, contractId, entityId, country, supplier, from, to, scope); a page joins by adding itself there. `checkFilters()` refuses any other key (country must be an ISO-2 code), and ids are checked against the organisation with `orgRefsError()` on create and on every filter change (`entityId` as `legalEntityId`). Who may do what: viewers of the inventory plus contract and project managers keep personal views (`viewRoles()`, 50 per person per page, unique name per person and page); only editors and admins share (`mayShare()`); the owner changes or deletes their own, and an admin may also change or delete a shared one, never someone's private one (`mayChangeView()`); a view is looked up inside the organisation and only among the caller's own or shared ones. Creating, changing or deleting a shared view is audit-logged (`saved_view.*`); personal churn is not. `GET` returns `href` for each view, built by `viewHref()`. Tests: `lib/saved-views/__tests__`, `tests/security/saved-views-tenancy.test.ts`. **The dashboard shows a "Views" menu** (`components/saved-views/saved-views-menu.tsx`, above the entity and country filters, only for `viewRoles()`): my views and shared ones (with the sharer's name), open a view (a plain link to the page with its filters, so the URL is the state), save the filters now set (the menu item is disabled with none set), share (editors and admins only; the control is hidden otherwise, the server decides) and delete (own views, and shared ones for admins; open and delete are sibling menu items so both are keyboard reachable). Tests: `components/saved-views/__tests__` (first component test in the repo, React Testing Library with `fireEvent`; Radix menus open from the keyboard in jsdom). **The records page filters through the URL** (`records/records-filters.tsx`, `records` in `SURFACES`): period, category, status, facility, contract, project site (`siteId`) and a supplier name fragment; native selects, the URL is the state (`router.replace`), the server page reads `searchParams` and the table refetches from its first page when the set changes, so a filtered list can be bookmarked, shared or saved from the same Views menu. `GET /api/orgs/{orgId}/activity-records` accepts `periodId`, `categoryId`, `reviewStatus` (enum, 422 otherwise), `facilityId`, `contractId`, `siteId` and `supplier` (case-insensitive contains, up to 64 characters); every filter narrows inside the organisation in the URL and none can widen it (`tests/security/activity-records-list-scope.test.ts`). Saved views on this page check the period, facility and contract ids against the organisation. **The suppliers page filters through the URL too** (`suppliers/page.tsx` is now a server page: it reads `searchParams`, offers the Views menu to `viewRoles()` and sends a signed-out visitor to sign in; `suppliers-filters.tsx` and `suppliers-table.tsx` are the client parts): name search (`q`), health band (`health`: healthy at 80 and above, at risk at 60, critical below; `healthOf()` in `lib/suppliers/filter.ts`, which the table's badge uses) and `trend`. The list API returns every supplier at once, so `filterSuppliers()` narrows it in the browser without a refetch. Fixed-list filters are validated by `ENUM_FILTERS` in `lib/saved-views` for every surface (review status, health, trend). **The submissions queue filters through the URL too** (`submissions/submissions-filters.tsx`, `lib/field-submissions/list-filters.ts`): the existing status tabs plus document type, period, facility and contract, all in the URL and saveable as views. `parseSubmissionFilters()` keeps only known keys with valid values (an old or malformed link still opens the page, unknown values are dropped, not refused) and `submissionWhere()` builds the where, always inside the organisation; the tab counts count each status under the other filters (`submissionWhere(..., false)`), the SLA banner stays organisation-wide. The tabs' links keep the other filters. The table's own cursor paging is dormant (the page loads `limit` rows and "Show more" reloads), so filters apply on the server only. **The calculations page filters through the URL too** (`calculations/calculations-filters.tsx`, `lib/calculation/run-list-filters.ts`): status, period and factor library (every library, so old runs can be found), saved as views like the other pages. `parseRunFilters()` drops unknown or malformed values instead of refusing, `runWhere()` always scopes to the organisation; the runs list still shows the newest 50 matching runs and the summary pills describe that list. A filter that matches nothing says so, rather than showing the first-run empty state. `ENUM_FILTERS` in `lib/saved-views` is now per page, because `status` means a submission status on one page and a run status on another. That completes the first four pages (dashboard, records, suppliers, submissions, calculations); any other page joins by adding itself to `SURFACES` and moving its filters into the URL.

**Arabic** (`i18n/request.ts`, `messages/{en,ar}.json`, `lib/i18n/ui-locale.ts`): the app's own screens are English. Strings are served by `next-intl` in its no-routing mode: the language is the `ui_lang` cookie, there is no middleware and no URL change, and only layouts that render a `NextIntlClientProvider` read the cookie (today only `(auth)`), so the marketing pages stay static. Arabic is a **pilot on the sign-in screen only**, behind `NEXT_PUBLIC_ENABLE_ARABIC_UI=true`, with a language switch (`components/i18n/ui-locale.tsx`) and `dir`/`lang` set on the sign-in panel. A missing translation falls back to English key by key (`mergeMessages()`); a test keeps the Arabic keys in step with the English. Its wording has not had a native review. To translate a screen: add its strings to both JSON files, call `useTranslations("<namespace>")`, and wrap its layout in `NextIntlClientProvider`. **Report PDFs have no Arabic support**: an embedded-font attempt was removed on the owner's instruction, so Arabic text in a report depends on the server's fonts and will print as empty boxes on Vercel. Not done: translating the rest of the app, an RTL layout audit (logical CSS properties), Arabic report text. Free monitoring and log drain steps: `docs/OPERATIONS_MONITORING.md`.

**Address search** (`lib/geo/address.ts`, `GET /api/orgs/{orgId}/geocode/autocomplete?q=&country=`, `components/address/address-picker.tsx`; env `GEOAPIFY_API_KEY`, server-side, free key from geoapify.com): typing three or more characters in a facility's address box (Settings, Operations: the add form and each facility row) asks our route, which asks Geoapify (OpenStreetMap data) for up to five suggestions; choosing one stores the street line, postcode, latitude and longitude, and fills country (ISO-2) and region. Editors only, 60 a minute per user; only the typed text and an optional two-letter country leave the server; 503 `GEOCODER_UNAVAILABLE` with no key or when the service fails, and the box stays a plain text field. The dropdown credits Geoapify and OpenStreetMap contributors. The page shows the position's Plus Code (`plusCode()`, Open Location Code, checked against the specification's examples), for places with no postcode; the Abu Dhabi workbook carries it too. Check Geoapify's current free-plan terms on storing results and attribution before relying on it at scale. Tests: `lib/geo/__tests__/address.test.ts`, `tests/security/address-search.test.ts`.

**Monthly checklist and "where to fix it" links** (`lib/completeness/monthly.ts`, `/orgs/{orgId}/checklist?month=YYYY-MM`, sidebar Data → Monthly checklist and Ctrl+K; editors): for the month just ended (or a chosen one) it lists, as `ChecklistItem`s with a `where` (the route through the app in words) and `fixes` (links), what is waiting on a person (field submissions, records in review, imports, accounting lines, bills in the inbox), what a regular source is missing (a facility and category recorded in at least two of the previous three months but not this one; billing ranges count in every month they cover; records with no facility are not tracked), records without evidence, no reporting period, and calculation out of date (approved records changed since the last run). On the 3rd of each month (`monthly-checklist` monitor, migration `20261005000076`, `lib/completeness/reminders.ts`) editors of organisations that hold records get one `monthly_checklist` notification when something needs action, linking to the page; the notification row for (person, month) is the "already sent" record. **Rule: wherever the app says something is missing, say where to add it and link to the page.** The pattern is `link?: { label, path }` on a check (CRP `CHECK_LINKS` in `lib/crp/plan.ts`, transition plan, TCFD), `CHECK_FIX_ACTIONS` in `reports/report-form.tsx`, and links inside the dashboard alerts; `lib/completeness/__tests__/fix-paths.test.ts` fails if a link points at a page that does not exist, so add new maps there. Records page filters are only `periodId`, `categoryId`, `reviewStatus`, `facilityId`, `contractId`, `siteId`, `supplier`; do not link to others. **Your emission factors** (Settings → Emission factors, `settings/factors`): the screen for `OrganizationEmissionFactor` (category, optional fuel/activity text, unit, kg CO2e per unit, country, dates, a required source), added through `POST /api/orgs/{orgId}/custom-factors`; the dashboard's no-factor alert links to it. Rule learning: lines confirmed in "Stage lines from your accounting system" keep their category on the sync log and count towards that supplier's learned category (`learnedSupplierCategories()`), alongside committed records.
